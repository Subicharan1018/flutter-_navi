# Smart Shuffle bake-off: every method, one protocol (2026-11-23)

Offline and read-only. Nothing on the server or in the app was changed. Results come first; my recommendation is at the end, separate from the tables.
All numbers are HR@10 in percent unless stated: how often the song actually played was in the method's top 10 of 2,486 songs.

## Read this first: errors in my earlier report

`docs/smart-shuffle-research-opus.md` (same day) contained mistakes of mine. They are fixed here, and these numbers replace it.

## Protocol

- Three 30-day test windows (cutoffs 2026-08-25, 09-24, 10-25); user state updates online; learned models are fitted only on data before each cutoff (re-rankers on the previous 60 days). Same 3,539 kept plays as the earlier report: owner 2,861, others 678.
- The log snapshot was copied on 23 Nov before play-events-v2 produced data, so it holds no `served_by` or `seconds_played`.
- Ties count half a place. Songs already heard in the session are excluded for every method (a within-session repeat penalty). 95% CIs are a cluster bootstrap over sessions (1,000 resamples); deltas are paired.
- Legacy exists for the owner only. Two limits remain: no Navidrome stars/play counts, and its impression totals come from today's database. It picks its queue with a small random jitter. An HR@10 hit means "in its real 10-song queue"; its HR@50 uses the 50-song queue, so its MRR is approximate.
- The blend's weights came from an earlier study on overlapping months of the same owner, and `rot_share_2d` was noticed on these windows, so both may be a little optimistic.

## Method names

| name | meaning |
|---|---|
| legacy | old hand-tuned `model.py` |
| v3 | current server LightGBM |
| usual_next | what usually follows this song |
| blend | recency + hour habit + usual-next (opener: + usual opener) |
| blend+rot2d | blend + 2-day rotation share |
| blend_no_opener_term / blend_flipped_opener | opener term removed / sign reversed |
| blend_no_opener+rot2d | opener term replaced by 2-day rotation share |
| hyb | blend top-100 re-ranked by LightGBM, pooled over listeners |
| hyb_no_audio_mood, logistic | hybrid without audio/mood features; logistic re-ranker |
| hyb_per_user | trained on the listener's own plays (only the owner had 100+ training groups) |
| hyb_start_only | trained on openers only; meaningful for openers only |
| *+guards | + cold rule, artist spacing, 3-hour repeat penalty |
| hyb_union_disc | stage 1 = blend top 80 + 20 discovery candidates |
| router: ... | one method for openers, another for next |
| g_* | stand-alone generators: album/film, composer/singer, audio neighbours, name neighbours, co-play of other listeners, others' popularity, recently added, g_rrf (rank fusion, never-played songs only) |
| X+1in5:Y | exploration: every 5th slot comes from generator Y (never-played songs only) |

**Invalid row:** `g_disc_lgbm` (and `+1in5:disc_lgbm`). I built its training groups badly: the positive was added even when the fused ranking missed it, so it learned "low rank = positive". It says nothing about whether a learned discovery ranker can work.

`g_recent_added` only has real dates for songs added after 18 Oct (the newest window), and may partly reflect songs a listener had just requested.

Owner: best next + best opener 28.7 (+12.8 vs v3, +4.0 vs blend); with the discovery slot 26.9, which costs 2.2 points on familiar songs and finds 3.1% of cold targets. Others: 24.9, and 22.9 with the slot, **below the plain blend (25.9)**. That choice rested on 83 plays, 18 of them openers, so it overfits; do not read it as a policy for other listeners.
